# Диагностика: «пароль неверный» при верных данных (Keenetic WebDAV)

Задача для следующего агента. Сначала диагностика, потом исправление. Не угадывай причину: по каждому шагу фиксируй, что именно проверено.

## Симптом

Пользователь вводит в приложении верные адрес `https://<имя>.keenetic.name/webdav/`, логин и пароль. Приложение пишет, что пароль неверный (ответ 401). В браузере с теми же данными вход работает.

## Что уже известно

Подтверждено:
- Приложение шлёт **Basic-авторизацию сразу, без предварительного запроса** (`FamilyCloudApp.kt`: `AuthInterceptor`; для проверки подключения — `WebDavClient.authenticated(...)`). Всё работает по **HTTP/1.1** (`protocols(listOf(Protocol.HTTP_1_1))`). `BasicAuthenticator` повторно ничего не делает, если заголовок уже отправлен.
- Сборка на GitHub (`main`, коммит `9f09360` и новее) уже содержит HTTP/1.1 и все правки по `docs/REVIEW.md`. Версия «latest» не старая.
- Контрольный запрос с компьютера через `curl.exe` (Basic, HTTP/1.1, `PROPFIND Depth: 0` и `GET`) с **правильным** паролем дал **401**. Та же 401 пришла и на заведомо неверный пароль. То есть сервер не принял Basic-данные и от `curl`, значит дело не в коде приложения.
- Заголовок `WWW-Authenticate` ни в одном ответе не был снят. Какую схему авторизации предлагает сервер, **неизвестно**.
- Имя домена резолвится в **два адреса** (`178.250.154.58`, `185.162.93.96`). После 4–6 запросов сервер перестал отвечать: TLS-рукопожатие обрывалось (`curl` код 35) или по таймауту (28), хотя TCP на 443 открывался. Возможно, сработала защита от подбора пароля на роутере или нестабильно работает облачный узел KeenDNS.

Не проверено, не выдавай за факт:
- Что сервер требует Digest.
- Что в `AppContainer` комментарий «Keenetic на HTTP/2 отвечает 401, а на HTTP/1.1 принимает» верен. Происхождение этого вывода неясно.
- Режим KeenDNS пользователя («прямой доступ» или «через облако»).

## Жёсткие правила

1. **Не стучись в сервер пользователя часто.** Роутер может блокировать адрес после неудачных входов. Не больше 3 запросов с учётными данными подряд, затем пауза 5 минут. Если TLS перестал отвечать — остановись и попроси пользователя подождать.
2. **Пароль не записывать** в файлы, коммиты, тесты, README, логи и отчёты. Спрашивай у пользователя. В командах передавай через переменную окружения текущей сессии, не через историю. Тестовые значения в коде — только вымышленные (`user`/`pass`).
3. Не публикуй имя домена и логин пользователя в репозитории (репозиторий может быть публичным). В документах — `<имя>.keenetic.name`.
4. Не меняй настройки роутера и не создавай/удаляй файлы на сервере. Допустимы только `PROPFIND`, `OPTIONS`, `GET`.
5. Ничего не пушь без согласия пользователя. Не говори «исправлено», пока пользователь не подтвердил вход на своём телефоне.

## Шаги диагностики

### 1. Узнай схему авторизации (главное)

Попроси пользователя выполнить на компьютере и прислать **только заголовки ответа** (без пароля):

```
curl.exe -i --http1.1 -X PROPFIND -H "Depth: 0" https://<имя>.keenetic.name/webdav/
```

Нужны: строка статуса, все `WWW-Authenticate`, `Server`, `Via`. Если `curl` по TLS не отвечает, пусть повторит позже или откроет адрес в браузере: DevTools → Network → запрос к `/webdav/` → заголовки **ответа**.

Дополнительно из DevTools для **успешного** запроса браузера (значение `Authorization` пользователю присылать **не нужно**, только первое слово):
- схема в `Authorization` (`Basic` или `Digest`);
- версия протокола (`h2` или `http/1.1`);
- метод и путь запроса (браузер может ходить на `/webdav/` или на другой путь).

### 2. Разбери результат

| Что пришло | Вывод | Дальше |
|---|---|---|
| `WWW-Authenticate: Digest ...` (одна схема) | Сервер требует Digest, приложение шлёт Basic | Шаг 3, реализация Digest |
| Две схемы (`Basic` и `Digest`) | Предпочесть Digest, Basic как запасной | Шаг 3 |
| `WWW-Authenticate: Basic realm=...` | Схема Basic, причина другая | Шаг 4 |
| Нет `WWW-Authenticate`, 401 | Прокси или облако режет заголовок | Шаг 4, пункт «облако» |
| Ответа нет, TLS обрывается | Блокировка или проблема узла | Попроси подождать, проверить из мобильной сети |

### 3. Если Digest: реализовать

Где: новый класс `DigestAuthenticator` в `data/webdav/`, подключается в `AppContainer.http` вместо `BasicAuthenticator` и в `WebDavClient.authenticated(...)` (там сейчас `Authenticator.NONE`). Готовые Digest-библиотеки не добавлять (правило проекта).

Требования:
- Разбор `WWW-Authenticate: Digest realm, nonce, qop, opaque, algorithm, stale, domain`. Поддержать `algorithm=MD5` (по умолчанию) и `MD5-sess`; `SHA-256` по возможности. `qop=auth` обязателен, `auth-int` не поддерживать.
- Вычисление: `HA1 = H(user:realm:pass)`, `HA2 = H(METHOD:uri)`, `response = H(HA1:nonce:nc:cnonce:qop:HA2)`. `uri` — путь и запрос запроса (как в request-line), `cnonce` — случайный, `nc` — 8 hex-цифр с ростом на 1.
- Заголовок: `Authorization: Digest username=..., realm=..., nonce=..., uri=..., algorithm=..., response=..., qop=auth, nc=..., cnonce=..., opaque=...`. Логин и пароль кодировать в UTF-8.
- При `stale=true` — один повтор с новым nonce. Всего не больше 2 повторов, иначе вернуть 401 без цикла.
- **Одноразовое тело (`PUT`).** `StreamingBody.isOneShot() = true`, поэтому ответ 401 на `PUT` повторить нельзя: поток уже прочитан. Решение: перед загрузкой делать лёгкий запрос (`PROPFIND Depth: 0` на папку или `OPTIONS`), получить nonce и **подписывать следующие запросы заранее**, увеличивая `nc`. Хранить `nonce`, `realm`, `opaque`, `nc` в памяти потока работы, не на диске.
- Пароль и вычисленные хэши не логировать. Отладочный интерцептор в `AppContainer` должен печатать только метод, код и (если нужно) имя схемы из `WWW-Authenticate`, но не значения.

Тесты (`MockWebServer`, без реального роутера):
1. Эталон RFC 2617: пользователь `Mufasa`, пароль `Circle Of Life`, realm `testrealm@host.com`, nonce `dcd98b7102dd2f0e8b11d0f600bfb0c093`, uri `/dir/index.html`, метод `GET`, `qop=auth`, `nc=00000001`, `cnonce=0a4f113b`, opaque `5ccc069c403ebaf9f0171e9517f40e41` → `response=6629fae49393a05397450978507c4ef1`.
2. Сервер отвечает 401 с Digest, затем 207: клиент повторяет запрос с корректным `Authorization`.
3. `stale=true`: один повтор, затем остановка.
4. `PUT` после предварительного запроса идёт сразу с подписью и не требует повторной отправки тела.
5. Басик-сервер продолжает работать (регресс).

### 4. Если Basic (или схема не ясна)

Сравни запрос приложения и браузера по заголовкам (без значения пароля):
1. Добавь во временный отладочный интерцептор (только `debuggable`-сборка) вывод: метод, URL без учётных данных, `response.protocol`, код, значение `WWW-Authenticate`, `Server`. Попроси пользователя прислать `adb logcat -s FamilyCloud` или скриншот. Не печатай `Authorization`.
2. Проверь, ходит ли браузер на тот же путь (`/webdav/` и `/webdav`), с каким `User-Agent` и версией HTTP. Если браузер на `h2`, а приложение на HTTP/1.1, попробуй разрешить `HTTP_2` **только для проверки подключения** и сравнить ответ. Прежняя запись в `AppContainer` («на HTTP/2 401, на HTTP/1.1 принимает») не подтверждена, проверь её, а не повторяй вслепую.
3. **Облачный режим KeenDNS.** Если домен работает «через облако», запросы идут через прокси KeenDNS и могут вести себя иначе, чем прямой доступ. Попроси пользователя открыть в роутере раздел KeenDNS и сообщить режим. При необходимости проверь доступ по прямому IP или из другой сети (мобильный интернет).
4. **Блокировка.** Спроси, не видел ли пользователь в журнале роутера записи о блокировке адреса после неудачных входов. Проверь вход через другую сеть.
5. **Права пользователя.** Убедись, что у пользователя роутера есть доступ к WebDAV и к нужной папке (раздел «Пользователи»/«USB-накопители»). Если браузер работает, вероятность низкая.

### 5. Ошибки приложения, которые стоит исправить в любом случае

- [x] Логин не обрезается по пробелам (`ConnectionViewModel.submit`, `WebDavRepository.test`). Клавиатура может добавить пробел после подсказки. Делать `login.trim()`. Пароль не обрезать, но показывать подсказку, если он начинается или заканчивается пробелом.
- [x] Сообщение о 401 должно называть схему, которую требует сервер («Сервер требует Digest», «Неверный логин или пароль (Basic)»), и предупреждать о блокировке после нескольких неудач. Для этого `WebDavError.Unauthorized` нужно расширить (например, `Unauthorized(scheme: String?)`) и обновить `errorText` и тесты.
- [x] Пользователю должно быть видно, **по какому адресу** шёл запрос после нормализации (`normalizeBase`), например, добавлен ли `/` в конец.

## Критерий готовности

1. Известна схема авторизации сервера (снята из заголовка ответа, не предположена).
2. Если нужна поддержка Digest, она реализована, покрыта тестами из шага 3, `./gradlew lintDebug testDebugUnitTest assembleDebug assembleRelease` проходит, CI зелёный.
3. Записано в `docs/SERVER_NOTES.md`: схема авторизации, режим KeenDNS, версия HTTP, особенности (без домена и логина пользователя).
4. Пользователь подтвердил: проверка подключения проходит, список файлов открывается, загрузка файла работает. Отдельно проверить загрузку файла больше 100 МБ (для Digest это важно из-за одноразового тела).
